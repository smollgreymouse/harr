# Исполнимый план: возобновление PR #15 про MCP-адаптеры

**Статус:** план работ; реализация и CI ещё не запускались.

**Цель:** дать проекту возможность выбирать несколько MCP-провайдеров одновременно, сохраняя нативную поверхность инструментов каждого провайдера и запуская upstream только по требованию. Проектная конфигурация выбирает разрешённые экземпляры провайдеров и привязанные к ним credential profiles.

**Ссылки и исходное состояние:** [PR #15](https://github.com/smollgreymouse/harr/pull/15) — открытый draft, только дизайн-документ; GitHub ранее показывал `mergeable=false`. В Harr подтверждены реестр серверов и `lifecycle: on-demand` (`common/mcp/manager.py`, `common/mcp/registry.json`). Gateway LeanCTX, в том числе правила `tools/list`, динамического namespace и фактического ленивого discovery, в исходниках Harr не найден; это обязательная проверка до выбора runtime-контракта.

## Архитектурные инварианты

1. Каждый экземпляр провайдера выставляет собственные инструменты с исходными именами, схемами и результатами. Внешнее имя инструмента однозначно квалифицируется экземпляром, например `<instance>::<tool>`.
2. Провайдеры не приводятся к общему семантическому API. Семантический фасад допустим отдельным, явно названным слоем, если для него появится самостоятельная потребность.
3. Запуск upstream и получение его `tools/list` происходят лениво для выбранного экземпляра. Обычный старт сессии не запускает все MCP-серверы.
4. Значения credentials хранятся только в пользовательском secret store Harr. Реестр хранит ссылки; project overlay выбирает разрешённый экземпляр и профиль. Overlay не содержит токенов и не может незаметно перенаправить credential на произвольный endpoint.
5. Запрос маршрутизируется к одному конкретному экземпляру и его профилю. Нет автоматического перебора токенов или переноса credential при совпадении имени сервиса.

## Этап 1. Проверить контракт LeanCTX и ленивый discovery

Это gate перед реализацией. Использовать текущую управляемую конфигурацию LeanCTX и тестовый MCP upstream; секреты не выводить в консоль или отчёт.

- Установить, как LeanCTX получает список доступных MCP-инструментов: при `tools/list`, при поиске или по запросу инструмента.
- Проверить, умеет ли gateway обновить список после ленивого запуска провайдера: динамический `tools/list`, уведомление об изменении либо предусмотренный gateway механизм discovery.
- Проверить, можно ли показывать инструменты с квалифицированными именами, сохраняя исходные `inputSchema`, описания, annotations и результаты вызова.
- Подтвердить по логам/счётчикам, что холодный запуск не стартует все upstream, discovery запускает только выбранный экземпляр, а вызов идёт к нему же.
- Определить, как поиск сужает кандидатов по описанию экземпляра, не требуя заранее запускать все серверы или получать весь каталог их инструментов.

**Gate:** если текущий протокол/LeanCTX не поддерживает нужный цикл discovery и публикации инструментов, остановить реализацию runtime и зафиксировать точный контрактный пробел для отдельного архитектурного решения. Не подменять это массовым запуском серверов или нормализацией поверхностей.

**Готово, когда:** есть проверяемая матрица возможностей и доказательство маршрута минимум для одного инструмента каждого целевого экземпляра.

## Этап 3. Установить свойства текущего secret store

До выбора реализации credential profiles точечно проследить memento backend и зафиксировать:

- место хранения байтов секрета и границу доступа к чтению;
- защиту на диске и права файлов/ключей;
- поведение backup/export/prune;
- операции обновления, ротации, удаления и инвалидирования кэша;
- маскирование значений в логах, ошибках и диагностике.

Использовать существующий интерфейс секретов Harr, если эти свойства подтверждены и он удовлетворяет требованиям ниже. Если backend не обеспечивает нужную защиту, остановиться и вынести изменение secret store отдельным решением; не добавлять значения credentials в project overlay.

**Требования:** profile имеет стабильный ID и отдельные секретные ссылки; он явно привязан к provider instance/account и утверждённому endpoint. Общий профиль может использоваться несколькими проектами только при явной привязке. Ротация меняет secret value атомарно, сохраняя ссылку; disable запрещает новые вызовы; отзыв на стороне провайдера считается отдельной операцией. Логи содержат только безопасные IDs и обезличенную причину ошибки.

## Этап 5. Реализовать по подтверждённому контракту

1. Добавить schema/loader/validator project overlay с fail-closed поведением и проверками доверенной привязки.

4. Подключить credential profile при запуске только соответствующего transport; не передавать невыбранные секреты дочернему процессу или соседнему HTTP upstream.
5. Обеспечить инвалидирование tool catalog/cache при изменении instance config или credential binding.
6. Добавить документацию команд настройки профиля и overlay, включая безопасную ротацию и отключение.

Конкретные runtime-файлы выбирать после этапа 1: `common/mcp/manager.py` уже рендерит записи upstream отдельно и запускает сервер по имени, но фактическое агрегирование/публикация `tools/list` выполняет LeanCTX и в Harr исходниках не обнаружено.

## Этап 6. Проверки и критерии приёмки реализации

Добавить автоматические проверки для следующих случаев:

- два экземпляра одного vendor namespace одновременно доступны и сохраняют разные наборы инструментов;
- разные providers сохраняют разные schemas/results; отсутствующий инструмент не маскируется заглушкой;
- холодный start не запускает upstream, discovery запускает только выбранный instance, повторный вызов использует его же;
- overlay с неизвестным instance, конфликтом имени, секретом в явном виде или неподтверждённым endpoint отклоняется;
- credential из профиля A никогда не используется для instance B, в том числе при 401/403, timeout или одинаковом домене;
- ротация и disable инвалидируют нужные соединения/каталог; секреты отсутствуют в логах, диагностике и сериализованных workspace overlays;
- существующие глобальные MCP-конфигурации продолжают работать без проектного overlay.
