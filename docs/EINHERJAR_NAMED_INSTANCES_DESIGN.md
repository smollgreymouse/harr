# Einherjar: named multi-instance setup and GigaCode compatibility

Status: design + implementation in PR #39; isolated test harness passes. Public installation and real CLI model sessions are not activated/tested here.

## Goal

Harr setup owns *any number* of independently named Einherjar instances. An instance is a stable MCP identity with its own backend adapter, executable/launch flags, workspace and session namespace, policy/skill binding, permission/timeouts and optional secrets. Multiple instances may use the same adapter with different settings. The existing GigaCode consumer contract MUST remain unchanged when migrated to this implementation.

## Short public API name

The public Harr CLI namespace is **`harr ein`** (short for Einherjar). `Einherjar` remains the conceptual/documentation name, not something users must type. Setup displays **Ein workers**. The existing, user-chosen MCP server name is not changed by this abbreviation; its canonical tool is `ein` for every instance. Do not expose `harr einherjar` as the required spelling. The shared skill keeps the existing `$einherjar-worker` identifier as a compatibility reference until a separate skill-name migration is approved; the CLI abbreviation does not silently break existing skills.

## Identity model

- `instance.id`: **required user-entered MCP server name at instance creation**, unique, stable, lowercase slug matching `[a-z][a-z0-9-]{0,62}`. Identity is immutable after creation; rename is explicit migration, never an implicit update.
- `instance.display_name`: editable human label, not an MCP identifier.
- `instance.adapter`: `gigacode`, `opencode`, `codex`, or a registered custom command-template adapter. This is implementation detail, not public identity.
- `instance.interface`: fixed `ein-v1` for **every** instance. It preserves the existing legacy GigaCode MCP behavior and argument/result schema, but deliberately renames the public tool to `ein`. The selected adapter never changes the public tool interface.
- `instance.profile`: one shared `einherjar-worker` skill and one shared policy template for **all** instances, including GigaCode. The old `$gigacode-executor` may remain as a temporary compatibility alias to the one shared skill, but must not diverge.
- `instance.enabled`: global selection state. Disabled instances remain in configuration and lose gateway/skill routing exposure, but historical session metadata is retained.

**The setup MUST prompt for a unique MCP server name for every newly added Einherjar; no adapter-derived, numbered or silent automatic naming, including duplicates of an adapter.** Check collisions with built-in/static and already registered MCP servers before saving. The existing `gigacode` identity is offered only when importing the legacy installation, and is never forced upon new GigaCode instances.

**One MCP gateway alias per instance**: e.g. `gigacode::ein`, `opencode-fast::ein`, `opencode-review::ein`. The old `gigacode::gigacode` tool name is intentionally retired when the migration is applied; no legacy alias or duplicate tool is created. The gateway manifest is generated by merging the static MCP catalog and the enabled instances. The canonical tool is always named **`ein`**, with the **identical** six actions `start|resume|status|messages|wait|cancel`, keys, limits, descriptions and response semantics for every instance. Never expose a `backend` override or `backends` action in a named instance tool. Instance binding is fixed before `start`; subsequent `resume/status/wait/messages/cancel` cannot switch instance/adapter.

## Proposed persisted configuration

Use `~/.config/harr/einherjar/instances.json` (schema 2) as the single source of truth; retain a migration/import path for the PR #39 `einherjar.json` backend-default config. The physical instance configurations are separate from the generated effective gateway registry. Illustrative data:

```json
{
  "schema": 2,
  "instances": [
    {
      "id": "gigacode",
      "display_name": "GigaCode",
      "enabled": true,
      "adapter": "gigacode",
      "interface": "ein-v1",
      "profile": "einherjar-worker",
      "execution": {"executable": "gigacode", "args": [], "environment_refs": [], "timeout_sec": 0},
      "workspace": {"mode": "caller"}
    },
    {
      "id": "opencode-fast",
      "display_name": "OpenCode Fast",
      "enabled": true,
      "adapter": "opencode",
      "interface": "ein-v1",
      "profile": "einherjar-worker",
      "execution": {"executable": "opencode", "args": [], "environment_refs": [], "timeout_sec": 0},
      "workspace": {"mode": "caller"}
    },
    {
      "id": "opencode-review",
      "display_name": "OpenCode Review",
      "enabled": true,
      "adapter": "opencode",
      "interface": "ein-v1",
```

Use separate protected `environment_refs` to Harr secret store; never inline secret values or copy vendor authentication directories into the sandbox. Strict allowlist for executable paths/args/environment. Preserve per-instance vendor auth/config directory selection only when explicitly configured; default isolation must not silently share vendor state. Do not claim process security isolation from XDG separation alone.

## Setup interaction

Add **Ein workers…** as a repeatable section in initial `harr setup` and `harr mcp configure`, not as N fixed catalog entries. Every Add flow starts by **asking the user to name the MCP server**, before selecting its adapter; the UI never quietly assigns `gigacode`, `opencode-2`, etc. The explicit MCP name determines the gateway namespace and is distinct from the optional friendly label. Setup loop:

```
Harr setup  >  External workers (Ein)

  NAME              ADAPTER      API                   ENABLED
  gigacode          GigaCode     ein-v1   yes
  opencode-fast     OpenCode     ein-v1   yes
  opencode-review   OpenCode     ein-v1   yes

  [A] Add worker    [E] Edit    [D] Disable    [R] Remove
  [T] Test selected [Enter] Continue

Add worker:
  MCP server name [required, unique]: ...
  Display name [optional]:           ...
  Adapter [GigaCode/OpenCode/Codex/Custom]: ...
  Interface [ein-v1] (fixed for all instances): ...
  Executable / args:                 ...
  Workspace mode:                    ...
  Secrets / env references:          ...
  Shared skill / policy:             einherjar-worker (fixed)
  Enable now?                        ...
  Validate and save
```

Non-interactive parity:

- `harr ein list`, `show NAME`, `add --id NAME --adapter ADAPTER`, `edit NAME`, `enable NAME`, `disable NAME`, `remove NAME`, `test NAME`, `doctor`.
- `harr setup --ein-file PATH` (or import subcommand) for reproducible CI/sandbox setup. No direct `--args 'shell command'`; accept safe argument arrays.
- Initial setup offers importing existing GigaCode configuration without changing its public identity.
- Edits validate and generate a **preview diff** of gateway names, skills, policy blocks and affected session ownership before apply. Apply is atomic with rollback (config temp file + fsync/rename and staged generated manifests). No systemd changes for on-demand instances.
- `test` checks executable/protocol via bounded probe and mock or opt-in real run; MUST NOT consume model tokens by default.

## Generated artifacts and runtime

1. Registry generator merges static `common/mcp/registry.json` *without a second hard-coded GigaCode server* with validated enabled instance definitions. Effective registry drives LeanCTX gateway and host integrations. Detect name collision with any static MCP or another instance; fail closed.
2. Per-instance MCP launcher: `harr-mcp-run --einherjar-instance ID` (or equivalent manager action) resolves immutable identity and loads config, then starts shared Einherjar engine with a compatibility-aware tool facade. Never trust user-provided `instance_id` in each tool call.
3. Namespaced cache: `.../harr/einherjar/<instance-id>/<workspace-hash>/<session-uuid>`; session metadata pins adapter id, instance id and config generation at creation. Updating an instance affects new sessions only; explicit action required for existing sessions. No cross-instance UUID lookups, cancel, resume or shared process control.
4. Tools published only for enabled instances. One shared skill and one shared policy template enumerate the *actual enabled instance tool names*. No separate per-adapter skills or behavior forks; the legacy `$gigacode-executor` remains only as an optional alias to this single canonical skill. Preserve user-authored policy and unrelated MCP settings.
5. If several workers use the same adapter, their executable args, environment, permissions, concurrency limits and session lifecycles remain independent; optional per-workspace concurrency conflict protection prevents two workers editing the same scope simultaneously.

## Codex Desktop live panel integration

Each enabled named Ein instance registers a separate **read-only direct MCP App**
`harr-ein-<name>-app::show_ein_live`. It takes an existing Harr session UUID,
never starts or resumes a worker, and returns only session/scope/status metadata
to the model. `poll_ein_ui`, `list_ein_ui` and panel lifecycle tooling are
app-only. Its UI resource is `ui://harr-ein-<name>/live.html`, with per-instance
session restoration, independent progress cursors, bounded long polling, and no
transcript consumption by the planner. GigaCode instances reuse their legacy
backend status/messages; other instances use the generic Ein backend.

The source integration is installed by `common/hosts/codex-config.py` on normal
host apply or by `harr ein apply`; only Harr-named app tables are reconciled.
Tests: `python3 tests/ein-app-panel.py` (two app identities, idempotent host
registration, disabled/removal reconciliation, fake detached session through
panel attach/poll/recovery). **A real Codex Desktop UI smoke is still required**
prior to declaring visual host parity; do not run it on the production Codex
installation for this PR without explicit user authorization.

## Non-negotiable GigaCode parity

Treat the pre-feature `gigacode_server.py` as an executable contract. `interface=ein-v1`, `id=gigacode` must preserve:

- public MCP `gigacode::ein` (intentional rename from `gigacode::gigacode`), no `backend` parameter; `action=start|resume|status|messages|wait|cancel`, exact argument keys and validation;
- `start` confirms observed vendor model/tool activity before claiming RUNNING, otherwise reports STARTING; generic process-alive is insufficient;
- `timeout_sec=0` unlimited; wait up to 1500s never cancels; one-shot status (no parent polling); compact public runtime fields;
- assistant-only progress, incremental revisions, app-only live panel where supported, explicit `messages`, and no leaking tool logs/JSON into model context;
- stable session UUID semantics, cancellation/resume, orphan protection, terminal DONE/ESCALATE/FAILED schema and acceptance evidence validation;
- one canonical shared Einherjar skill that subsumes the full existing `gigacode-executor/SKILL.md` behavior, with an optional compatibility alias `$gigacode-executor`; migrate generated routing and documentation to `gigacode::ein` without divergent instructions;
- existing tests `tests/gigacode-bridge.py`, `tests/gigacode-lifetime.py`, MCP app tests and Desktop/UI streaming coverage must pass through the **new façade**, not only through the unchanged legacy server.

There are *known differences now*: PR #39 Einherjar has `backend` and `backends` action in public schema; it returns RUNNING based on a different startup path and does not implement the full legacy live-progress surface. Therefore **do not replace legacy GigaCode with the generic worker directly**. Implement the single `GigaCodeCompatibleFacade` used by **every** named instance and close parity gaps, or reuse the legacy MCP adapter over the new core until its behavior is demonstrably equivalent. No removal of old implementation before differential tests pass.

## Implementation sequence / acceptance

1. Add schema v2 + strict validators, migration/import and atomic persistence. Test missing name, explicit name prompt, duplicate adapter with different user-chosen MCP names, static/dynamic MCP name collisions, malformed ids, unsafe commands, duplicate adapters with different configs, updates without unintended session mutation.
2. Implement generated registry/gateway and per-instance launcher. Test two OpenCode instances plus fake custom with distinct MCP server names, each exporting precisely the same `ein` tool JSON schema and actions; verify no gateway or skill collisions.
3. Add TUI setup loop and noninteractive CLI sharing the same atomic mutation API. Test add/edit/disable/re-enable/remove, repeat setup idempotence, cancellation rollback.
4. Add instance-aware session namespaces, pinning and cross-instance access denial. Test kill/cancel and restarts; ensure cleanup targets only owned jobs.
5. Implement shared GigaCode-compatible façade for **all** instances and differential contract suite against old server: introspected tools/list JSON, all action states, protocol progress, startup confirmation, error envelope and desktop panel. Only migrate the default GigaCode instance when this suite is green, updating generated routes to the deliberate new tool name.
6. Perform isolated harness smoke tests with fake agents; real CLI/model probes require explicit opt-in. Never run/modify Codex during this effort unless separately authorized.

**Decision**: no provider-specific branches in Einherjar core. All instances expose one identical GigaCode-compatible MCP action/argument/result API via the `ein` tool, including the GigaCode instance; no legacy tool-name alias; adapter code translates vendor CLI syntax/events; one shared skill/policy routes to the chosen named instance. This keeps N instances scalable without sacrificing GigaCode's existing guarantees.
